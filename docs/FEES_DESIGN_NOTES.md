# Fees: design notes to carry into the fees feature (pilot item 6)

Status: **notes only, nothing designed or built.** Recorded 2026-11-10 from Smirthi so they are not lost. The full
design and acceptance checks come first, and are approved, before any fees code.

## Principle (from Smirthi)
Each college uses **its own Razorpay account**. Fees settle straight into that college's bank account. **Money never passes
through our account.** We are software, not a payment collector.

## What follows from it
- **Per-college keys, stored encrypted.** Each tenant stores its own Razorpay key id, key secret and webhook secret in the
  shared encrypted-credentials table (designed in `docs/WHATSAPP_DIGEST_ACCEPTANCE.md`, built with that feature).
  Encrypted with a key from the environment, shown only as the last four characters, replaceable, audited without their
  values, and never in logs, error pages or the HTML.
- **No platform Razorpay key exists.** The code has no setting for one, so a bug cannot route a payment to us. A test
  asserts every payment call uses the current tenant's credentials and fails if none are set.
- **Tenant isolation matters most here.** A College A payment must never be created, verified or refunded with College B's
  keys, and a college's webhook must not be able to mark another college's fee paid. Tests first, as always.
- **Webhooks resolve the college from the host name** (each college has its own subdomain, so the webhook URL is
  `https://<college>.ourerp.in/...`). Unlike the WhatsApp webhook, no lookup table is needed. Signatures are checked
  with that college's webhook secret; payments are matched by Razorpay order id and are idempotent (a repeated webhook
  never double-credits a student).
- **Test and live mode** are stored per college and shown clearly; live keys are never accepted on a non-production
  environment, and test keys never on production **(to decide)**.
- **Setup check**: when an admin saves keys, make one harmless authenticated call to confirm they work, and say plainly
  if they do not. The secret is never echoed back.
- **Amounts** are stored in paise (integers), never floats. Receipts and reminders are generated by us; the money record
  is Razorpay's, reconciled against our fee ledger.
- **Rotation and revocation**: an admin can replace keys at any time; old keys are overwritten, not kept.
- **Our role in disputes and refunds**: we show status and history; refunds are made by the college in its own Razorpay
  dashboard unless the design says otherwise **(to decide)**.

## Questions for the fees design
Fee structure per programme/batch/regulation; instalments and due dates; concessions and scholarships; late fines
as configuration, not code; part payments; refunds; cash and cheque entries recorded by office staff; receipt numbering
rules per college; Razorpay UPI/card/netbanking only or also payment links; what a student or parent sees; fee
reminders through the WhatsApp sender (needs its own approved templates).
